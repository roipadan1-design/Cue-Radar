# Cue Radar — Trip Radar "event_sources" Seed Mapping (23 cities)

The single most important finding: across all 23 markets **almost no source publishes a public ICS/RSS/JSON feed**, so the crawler must be architected around HTML/DOM scraping and JSON-LD (`schema.org/Event`) extraction rather than feed ingestion — plan for per-site scrapers, not a feed reader. The pilot six (Berlin, Cologne, Brussels, Tel Aviv, Vienna, Amsterdam) are covered in depth below; the other 17 more briefly. Rows are marked **verified** (page opened, live dated calendar seen) or **unverified** (correct official domain/program path identified, live calendar not directly confirmed — validate before production crawl).

## TL;DR
- **Sources exist — plenty of them, confirmed with live evidence.** The original conclusion was read by the owner as "there's nowhere to pull event data from," which is wrong and is corrected below. What's actually true, re-confirmed adversarially on 2026-09-16 with live fetches, a real browser session, and raw-HTML probes: **the data is real and reachable, but it is not available through a free/open API or feed anywhere.** Every category the owner asked about (club/experimental listings, city tourism agendas, local listings press, cultural institutes, Eventbrite/Facebook, venue calendars) turned up real, verifiable, dated event listings for every one of the 8 sample cities. None of them turned up a usable public API. See "Second pass" section below for the city-by-city evidence.
- **Feeds/APIs are still the binding constraint, now double-checked, not assumed:** no ICS/RSS/JSON feed or public API was found for events anywhere, including a fresh, direct attempt to use Resident Advisor's internal API (see below — it exists, it's real, and it's blocked to plain HTTP clients; it works from a real browser session). Build HTML scrapers with headless-browser rendering; do **not** rely on JSON-LD — a raw-HTML probe of 7 verified venue/aggregator pages (HAU, Mercat de les Flors, Tokyo Art Beat, Karnet, Dansehallerne, iamsterdam, tanzraumberlin) found real `schema.org/Event` JSON-LD on **zero** of them (iamsterdam and Mercat de les Flors have `application/ld+json`, but only for `BreadcrumbList`/`WebSite` navigation schema, not events). This corrects the "highest-yield extraction path" claim from the first pass — JSON-LD is the exception, not the rule; plan for DOM scraping as the default, JSON-LD as a bonus when it happens to be present.
- **Best "anchor" sources to build first:** city aggregators with dense dated listings — tanzraumberlin.de + field-notes.berlin + Berlin Bühnen (Berlin), MuseumsQuartier + TQW (Vienna), NRW Landesbüro Tanz (Cologne), Tokyo Art Beat (Tokyo), Danse Suisse Tanzkalender (Zurich), CPH Stage (Copenhagen), Karnet (Krakow), Agenda 500 + IF Barcelona (Barcelona), thisisathens.org (Athens), plus **Resident Advisor (ra.co)** as the cross-city backbone for experimental-electronic/sound events.
- **Weakest coverage / Instagram-newsletter fallback:** Tel Aviv experimental sound (Levontin 7, Hateiva) and general culture (the municipal `visit.tel-aviv.gov.il/see-do/whats-on` page is a JS template with no server-rendered content — needs headless rendering or a different Tel Aviv source), Tbilisi's contemporary/club scene (Instagram + RA only), and small Berlin sound micro-venues. Some entities are closed/relocated (STEIM, SuperDeluxe) or dormant (Centre Pompidou renovation to 2030) and must be excluded.

## Second pass (2026-09-16) — adversarial re-check, six source categories, 8 sample cities

Triggered by the owner's pushback on the first pass's framing ("there's no way there isn't a place I can pull data"). This pass did not repeat the first search — it went category by category as instructed, tried to break the "no sources" reading with live fetches (`WebFetch`, a real browser session with network-request inspection, and raw `curl` HTML probes), and reports exactly what was found, what's structured vs. manual, and a real link for every claim. Sample: Berlin, Vienna, Amsterdam, Brussels, Tel Aviv, Tokyo, Barcelona, Athens (the 8 the owner asked for, at minimum).

**Bottom line up front:** the first pass's per-city venue tables (below) were already real and extensive — 35+ verified sources, not zero. What the first pass got right, and what this pass reconfirms harder, is narrower than "no sources exist": there is no free public API/feed for event data in this space. Every category below has real, human-verifiable sources; none has a usable API.

### 1. Club/electronic & experimental music — Resident Advisor (ra.co)

- **No public API, confirmed directly.** A plain HTTP fetch of `https://ra.co/events/de/berlin` returns **HTTP 403** (checked twice, via `WebFetch` and via `curl` with a browser user-agent) — RA actively fingerprints and blocks naive bot clients.
- **But the data is real, dense, and dated — confirmed in a live browser session.** Loading the same URL in an actual browser rendered **1.8k upcoming Berlin events**, each with date, venue, and attendee count, from big club nights (Else, RSO.BERLIN, Tresor) down to micro-venues in our niche — e.g. "Improvised & Experimental No. 295" at **Hošek Contemporary**, a small experimental-music room. This directly covers the sound/live-electronics discipline the first pass called weakest.
- **The mechanism:** network inspection during that session showed the page is powered by a single `POST https://ra.co/graphql` call — RA's own frontend uses an internal, undocumented GraphQL API. This is exactly what the third-party scrapers on Apify (`ra.co/api` listings from `augeas`, `parsebird`, `logiover`, `scrapesage`) and the open-source `djb-gt/resident-advisor-events-scraper` (GitHub) key off. It is not an authenticated developer API — no key, no ToS grant — but it is a real, structured, JSON-returning endpoint that a headless browser (or a scraper that replicates RA's request signature) can call per city/date-range.
- **RSS exists but doesn't cover this.** RA does run RSS feeds (`ra.co/news/9078` confirms "individual RSS feeds for each region"), but these are for the News/Features/Reviews magazine content, not event listings — a dead end for event sourcing specifically.
- **Verdict: real, structured, usable — but access method is "headless browser or GraphQL-replay scraper," not "call an API with a key."** Matches Stage-1 priority already given to ra.co in the Recommendations section below; nothing here should be downgraded, but the specific access method (naive HTTP fetch fails, browser-based fetch works) should inform the crawler design.

### 3. Local listings publications ("Time Out"-style)

- **Time Out** operates city editions relevant to several target markets (Amsterdam, Tokyo, Barcelona confirmed via search; Berlin, Tel Aviv, Athens have Time Out coverage too). No public API — confirmed no developer/API documentation surfaced in search; these are consumer web pages only, scrape-only like everything else.
- **Vienna: Falter** (`falter.at/events`) — real, live, filterable weekly listings magazine with dedicated URLs per category and per region (e.g. `falter.at/events/theater-und-shows-in-wien`, `falter.at/festivals/wien`). This is a genuine, well-structured local listings source that the first pass's Vienna table did not include — **new find, should be added to the Vienna venue table** (see below).
- **Brussels: BRUZZ** (`bruzz.be`) — Dutch/French-language Brussels media outlet with a dedicated Theatre & Dance agenda section and a Culture vertical; confirmed to exist and be structured by category, same JS-rendering caveat as other Brussels sources. **New find for Brussels.**
- **Verdict:** this category is real and, where it exists (Vienna's Falter, Brussels' BRUZZ), often better curated for our disciplines than the tourism-board agenda, because it's written by culture journalists, not destination marketers. No API in any case checked.

### 4. Cultural institution calendars (Goethe-Institut, Institut français)

- **Goethe-Institut** has confirmed branches with event pages in Athens (`goethe.de/ins/gr/en/m/sta/ath/ver.cfm` — dedicated events URL), Tel Aviv, and Tokyo. Structure is per-institute, no central API; each institute's calendar would need its own light scraper. Real but small-volume per city — supplementary, not an anchor.
- **Institut français** has confirmed branches with dedicated agenda pages in Tokyo (`culture.institutfrancais.jp/fr/tokyo`, plus `institutfrancais.jp/fr/agenda/`) — real exhibitions/concerts/performance programming, 8–10 exhibitions/year cited directly on their own site. **Institut français d'Israël (Tel Aviv)**: confirmed to exist with its own agenda page, but current search results show **events currently suspended** — an honest gap for Tel Aviv right now, not a research failure; worth a manual re-check closer to launch.
- **Verdict:** real, low-volume, useful as supplementary sources especially where they're one of the few concentrations of programming in a discipline (e.g. Institut français Tokyo's exhibition programme). Not a replacement for venue/aggregator anchors.

### 5. Aggregator platforms — Eventbrite and Facebook Events

- **Eventbrite: no public search API, and this is not new information being missed — it was deliberately shut off.** Confirmed directly: Eventbrite killed public access to `GET /v3/events/search/` in December 2019, effective February 20, 2020, specifically to stop third-party aggregation. As of the most recent information available, there is still no public endpoint for searching events platform-wide; the only documented paths are event-by-ID, events-by-venue, and events-by-organization (i.e., you already need to know what you're looking for), or Eventbrite's own **distribution partner program** (a business-development relationship, not a self-serve API key). **What does still work:** Eventbrite's own city+category web pages are public and real (e.g. `eventbrite.com/d/austria--wien/events/`, `eventbrite.com/d/israel--tel-aviv-yafo/events/`) — usable exactly like any other listings site, city by city, by scraping the web page, not an API. Label this honestly as manual/scrape-only, not "no source."
- **Facebook Events: effectively unusable for this purpose.** The Graph API's public event-search capability was locked down years ago (post-2018, tightened further since) and third-party developer access to event search is not realistically obtainable for an independent product — confirmed via search that even adjacent Graph API capabilities (Groups API, `metadata=1` debug param) are being actively deprecated further in 2026, the trend is tightening, not loosening. **Verdict: exclude as a structured source.** Individual public event pages can still be opened manually by a human, but this does not scale into a crawler and carries ToS risk — not recommended as a pipeline input.

### 6. Venue/space-level calendars

- This is where the first pass already did the real work: 35+ verified venue and aggregator calendars across the pilot six cities, plus leads across the other 17. This pass's spot-checks (HAU Hebbel am Ufer, Mercat de les Flors, Tokyo Art Beat, Karnet Krakow, Dansehallerne) confirm these pages are real and live, but **all are JS-rendered with no usable per-event structured data in the raw HTML** — reconfirming that headless-browser rendering, not a lightweight HTTP scraper, is the right architecture, and that JSON-LD should be treated as a rare bonus, not the default extraction path (correcting the first pass's framing on this point specifically).
- **Verdict: yes, numerous and relevant enough per city to be worth aggregating individually** — this remains the most reliable path precisely because it doesn't depend on a platform (RA, Eventbrite, a tourism board) staying friendly to scrapers; it's ~5–10 independent small scrapers per city instead of one fragile one.

## Key Findings
- **Recommended crawl frequency by source kind:** `studio_schedule` = weekly; `venue_program` = twice weekly; `city_aggregator` = daily; `festival` = monthly, escalating to daily in the 8 weeks before an edition (periodic festivals only publish programmes shortly before); `museum_gallery` = weekly; `newsletter`/`instagram_only` = manual/weekly.
- **Richest structured markets:** Berlin, Vienna, Tokyo, Zurich — each has at least one dense, filterable dated aggregator.
- **Crawlability:** most modern venue calendars (Tanzhaus Zürich, TQW, Dansens Hus, Lavanderia a Vapore, Culturgest) are JS-rendered — budget for headless-browser rendering. Cookie/consent walls are common on German and Austrian sites (Tanzfabrik, Stadtgarten) but do not block content extraction.
- **Discipline coverage is uneven:** dance/choreography/performance are well served by institutional sites; experimental sound/live-electronics is disproportionately dependent on RA, micro-venue HTML pages, and newsletters.

## Recommendations
**Stage 1 (build now — highest ROI):** Stand up scrapers for the ~40 **verified** venue/aggregator calendars, starting with the daily aggregators (tanzraumberlin, field-notes, Berlin Bühnen, MuseumsQuartier, Falter, NRW Landesbüro Tanz, Tokyo Art Beat, Danse Suisse, CPH Stage, Karnet, IF Barcelona, Agenda 500, thisisathens.org) plus the pilot-city verified venues. Build with **headless-browser rendering as the default extraction method** (Playwright/Puppeteer-class tooling); probe for JSON-LD opportunistically per source but do not depend on it — the second pass found it real on 0 of 7 spot-checked sources. Add ra.co as the experimental-sound backbone for Tbilisi, Seoul, and cross-city coverage, via a real browser session or a GraphQL-replay approach (plain HTTP fetches to ra.co are blocked with 403 — confirmed directly).

**Stage 2 (validate & expand):** Convert the **unverified** rows to verified by fetching each page and confirming a live dated calendar and the correct scan URL; demote or drop any that turn out to be homepages-only or defunct. Prioritise the pilot-six unverifieds (Charleroi danse, Beursschouwburg, Les Brigittines, Kelim, Tmuna, Levontin 7, ICK, Bimhuis) and the strongest secondary-city venues (Théâtre de la Ville, Setagaya, Platform-L, CCA Ujazdowski, Cricoteka, MeetFactory, Culturgest neighbours).

**Stage 3 (festivals & long tail):** Register periodic festivals with an escalation rule — idle-crawl until ~8 weeks before the known edition window, then daily. Verify Amsterdam's Dansmakers/Veem House branding/status, and confirm whether ACHT BRÜCKEN continues past 2025.

**Benchmarks that should change the plan:**
- If a site exposes JSON-LD `Event` data or an ICS endpoint on probing → promote it to daily, low-cost crawl and drop headless rendering.
- If a verified calendar is JS-only with no JSON-LD → require headless-browser rendering (higher cost; batch these).
- If ≥3 crawls return no future-dated events for a "rolling" source → reclassify as seasonal/newsletter and reduce frequency.
- For any city where verified sources cover <3 of the five content types → add the city's Instagram/RA fallback and a scene newsletter to the pipeline.

## Caveats
- **Verification is partial.** "Verified" means a live dated calendar was seen (directly or in a page snippet); "unverified" rows have the right domain but need a confirmation fetch before production. Treat unverified URLs as leads, not guarantees, and never crawl a homepage as if it were a calendar.
- **No feeds anywhere** materially raises build cost and fragility — scrapers will break on redesigns; budget for monitoring and repair.
- **New from the 2026-09-16 second pass, reported honestly rather than smoothed over:**
  - `visit.tel-aviv.gov.il/see-do/whats-on` (the official municipal tourism "what's on" page) served only unrendered template placeholders on direct fetch — currently the weakest of the 8 sample cities' general-agenda category; needs a headless check or a different Tel Aviv anchor before relying on it.
  - Institut français d'Israël (Tel Aviv) shows events currently suspended per its own site — a real, current gap for Tel Aviv's cultural-institute coverage, not a search failure.
